# 有据 · 文档问答引擎

把一批 PDF 文档变成能问、能溯源的知识库。**回答永远带原文出处**，答不出时明确说"找不到"。

> 名字取"有据可查"。在这个大模型随手编造的时代，**每句话都能追到原文**反而是稀缺品。

## 三套语料

同一个引擎，装上三种完全不同的语料，每种都针对性地调过检索与提示词。

| | 语料 | 文档 | 切块 | 核心机制 |
|---|---|---:|---:|---|
| **A** | 华润微 2019–2022 年报 | 4 | 2,955 | 答全 + 表格读法 + 跨年 |
| **B** | 半导体 5 家公司年报 | 15 | 10,947 | **多源归因**：每个结论标明出自哪家公司 |
| **C** | 华润微全套管理制度 | 10 | 627 | **精确到条款**：引用到「《制度名》第X条」 |

语料来源：**巨潮资讯网**（沪深交易所指定的法定披露渠道），全部为公开信息。

## 它解决什么

一份 200~300 页的年报，想知道"公司靠什么赚钱"要翻到 30 页左右；
想知道"研发方向"又是另一处；"有哪些风险"再翻一遍。

这套系统把它变成一句话。**用户省下的是翻找的时间，不是判断的脑力** ——
所以设计上刻意保证了一件事：**每个答案都能追到原文**。

## 架构

```
构建期（一次性，由运作者承担）
  PDF ──解析──> 清洗 ──> 结构感知切块 ──> 去重 ──> 导出为静态 JSON
  成本：约 40 秒/份

运行期（用户提问时）
  浏览器 ──按需下载语料──> 本地 BM25 检索 ──> 拼上下文
                                                    │
                                免费后端（只转发）───┴──> 大模型 ──> 带出处的回答
```

**关键：检索完全在浏览器里完成。** 全程只需要下载语料文本，
不需要嵌入模型、不需要 ONNX、不需要 WebAssembly。

### 大小管理

| 语料 | 原始 | gzip | 何时下载 |
|---|---:|---:|---|
| A 单公司年报 | 2.65 MB | 0.61 MB | 用户切到 A 时 |
| B 行业知识库 | 10.17 MB | 2.14 MB | 用户切到 B 时 |
| C 制度知识库 | 0.40 MB | 0.09 MB | 用户切到 C 时 |
| **合计** | **13.22 MB** | **2.84 MB** | 按需，不预载 |

三个语料**互不下载**：用户看 A 就只下 0.61 MB（gzip 后）。
单文件最大 10.17 MB，低于 Cloudflare Pages 的 25 MB 上限。

## 检索策略：只用 BM25

在 60 道真实问题上的对照实验：

| 策略 | Top-6 命中 |
|---|---:|
| 纯向量检索 | 22% |
| **BM25 关键词** | **92%** |
| RRF 等权融合 | 47% |
| 向量top3 + BM25top3 | 82% |

**结论是只用 BM25。** 原因：中文企业文档的提问自带精确术语
（"所得税影响额""对外投资审批权限"），关键词匹配一击即中；
而向量模型会把整页内容平均成一个语义向量，具体术语被稀释。

> 这个结论**和同一个人的小说问答项目（santi）正好相反** ——
> 那边提问是模糊口语，混合检索也没优势。
> **同样是 RAG，语料特性不同，最优策略相反，结论不能照搬。**

### 三个针对性修复（都是实测出来的）

| 问题 | 现象 | 修法 |
|---|---|---|
| B 被单一公司垄断 | 问"这几家公司"，只召回相关词密度最高的那一家 | **按公司分组检索**，每家保底取 2 条 |
| A 跨年召不全 | 问"2019到2022年营收"，含数值的块排 18~92 名，Top-8 一条都没有 | **按年份分组检索**，每年保底 4 条 |
| 科目名与提问不一致 | 利润表写"营业**总**收入"，用户问"营业收入"，字符二元组匹配不上 | **术语同义词扩展**，块从第 20 名升到榜首 |

## 切块质量

切块是检索的地基，这里每一项都是测出来的：

| 指标 | A 年报 | B 行业 | C 制度 | 为什么重要 |
|---|---:|---:|---:|---|
| 超长块（>900字） | 0.00% | 0.25% | 0.00% | 超过模型窗口会被**静默截断**，等于检索不到 |
| 标题路径覆盖 | 99.9% | 99.9% | 98.7% | 没有路径的块，召回了也不知道出自哪 |
| 正文重复 | 0.0% | 1.0% | 0.0% | 重复块会挤占 TopK 名额 |

### 切块逻辑的三处修正

1. **层级扩到 5 层**（章 / 节 / 条 / 一、 / （一））
   年报只用「节」，制度文档还用「章」和「条」，原来只认「节」会丢上下文。
2. **「条」的路径只放编号**
   制度里标题和内容是同一行（"第十条 公司股份只有一种类别。"），
   不处理的话整条正文会跑进标题路径。
3. **模板重复块剔除**
   跨公司完全相同的块（承诺表表头、审计准则套话）直接剔除；
   同公司跨年完全相同的块只保留最新年份。实测 A/B 各有 10~12% 是这类内容。

## 明确不做的事

| 不做 | 为什么 |
|---|---|
| 用 RAG 回答精确财务数据 | 企业实践里这类需求走数仓 / Text2SQL。实测三大报表只能覆盖这类问题的 **1.4%**，用文档检索查数字是拿短板碰长板 |
| 让模型替用户做计算 | 需要精确计算时应让代码算，模型只负责找与说 |
| 假装什么都能答 | 答不出时明确说"找不到"，并列出材料中确实有的相关年份 |

## 安全

- **API key 从不进入浏览器**：key 存在 Cloudflare 的加密环境变量里，
  浏览器只发送已经拼好的提示词，服务器补上 key 后转发。
- 请求体大小上限 60 KB，避免被当作通用接口滥用。

## 已知限制

- **制度文档的版本**：去重时按文件名里的年份判断新旧，而规范化后的文件名不含年份，
  可能保留了旧版本。要彻底解决需要在下载时记录公告日期。
- **不做身份隔离**：所有访客共享同一份语料，没有权限体系。
- **只支持文本型 PDF**：扫描件没有 OCR。
